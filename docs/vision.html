Platform blueprint · vision, design, roadmap

CodeBrain

A repository stores code. It does not store understanding — so every agent that touches it rebuilds a mental model from scratch, gets it partly wrong, and throws it away. CodeBrain turns a repository into a Brain: a durable, versioned, cited model of the system that agents and humans share across the entire software lifecycle.

Draft v0.1 14 Aug 2026 Greenfield · legacy · systems-of-systems
01

The bottleneck is comprehension, not capability

Coding agents are good enough to do the work. They fail on real systems for a duller reason: they never get to know the system.

Every session starts amnesiac. The agent greps, opens a handful of files, assembles a fragile model inside its context window, acts on it, and at session end the model evaporates. The next agent — or the same agent tomorrow — pays the full cost again, and reaches a slightly different conclusion. Understanding is re-derived thousands of times, inconsistently, and never accumulates anywhere.

Meanwhile the truth about the system is real, but scattered across places no single retrieval pass reaches: structure lives in the AST, intent lives in git history and closed pull requests, operational reality lives in CI configs and deploy scripts, constraints live in tribal knowledge, and the domain model lives in the head of someone who left in 2019.

02

What we are building

CodeBrain compiles a repository into a Brain — and keeps it true on every commit — so that any agent or engineer starting any lifecycle task begins informed instead of blind.

A Brain is not a wiki, and not an embedding index. It is a structured, layered, provenance-carrying model of one software system, stored beside the code, versioned with the code, and reviewed like the code. It is built deterministically where possible, enriched by language models where necessary, and — crucially — verified by execution where the claim is executable.

Two things come out of it. For humans, an Atlas: the onboarding document that is always current because it is generated, not maintained. For agents, a Context Pack: a task-scoped, budget-bounded, fully-cited bundle answering the only question that matters at the moment of work — what is the minimum sufficient context to do this correctly?

The second is the real product. Agents rarely fail because the model is weak; they fail because they were handed the wrong thousand lines. Retrieval quality, not model quality, is what an autonomous software factory runs out of first.

Why this, why now

Model capability crossed the threshold where multi-step code change is routine. Context windows grew, but system size grew faster, and relevance degraded — more context is not better context. And the largest market is not greenfield: most software in the world is legacy, and legacy's defining problem is precisely lost understanding. A system that reconstructs and preserves understanding is worth more on a twenty-year-old codebase than on a new one.

03

Principles

These are the commitments that decide the arguments later. Each one closes off a tempting shortcut.

iDeterministic first, inference last.Anything derivable from the AST, the manifests, the git log, or the CI config is derived that way — free, reproducible, offline, and exact. Language models are used only where meaning genuinely cannot be computed.
iiProvenance or it didn't happen.Every node, edge, and claim carries evidence spans, an extraction method, a confidence, and the commit it was true at. An agent can demand only verified facts for a risky refactor. A Brain that confabulates silently is worse than no Brain.
iiiContext is the product.The graph is substrate. Success is measured by whether a packed context makes an agent finish a task it would otherwise fail — not by node counts or coverage percentages.
ivClaims must be falsifiable."The test command is pytest -q" is a hypothesis until CodeBrain runs it. Executable claims get executed; verified facts are promoted, refuted ones demoted. This is the line between a Brain and documentation.
vThe Brain is code.It lives in the repo, diffs on pull requests, and gates CI when it drifts from HEAD. Understanding that isn't versioned alongside the thing it describes goes stale by default.
viUnknowns are first-class.A partial Brain beats no Brain. Gaps are recorded as open questions and surfaced in packs, so an agent knows the edge of the map instead of walking off it.
viiRead-write, not read-only.Agents contribute back: what they learned, what the Brain got wrong, which constraint bit them. The asset compounds with use.
viiiPluggable, not language-locked.Extractors are providers behind a stable schema. New languages, frameworks, and third-party graph tools plug in without touching the core.
04

Conceptual design — eight layers

A Brain is a stack. Each layer answers a distinct question an agent actually asks, is sourced differently, and earns a different level of trust. Lower layers are cheap and certain; higher ones are expensive and interpretive.

L0 CorpusWhat is this thing, and what is in it?filesystem · manifests · licences · language mix · vendored code EXTRACTED
L1 StructureWhat exists, and how is it wired together?AST · symbols · imports · call graph · type graph · module boundaries EXTRACTED
L2 BehaviorWhat does it actually do when it runs?entrypoints · HTTP routes · jobs · queues · DB access · env & config · side effects DERIVED
L3 SemanticsWhat does this mean in the business?domain entities · bounded contexts · capabilities · business rules · ubiquitous language INFERRED
L4 IntentWhy is it like this, and what has it survived?git archaeology · churn & hotspots · co-change coupling · ADRs · PR threads · incidents DERIVED
L5 OperationsHow do I build, test, run, and ship it?CI pipelines · scripts · containers · IaC · environments · ownership EXTRACTED
L6 ConstraintsWhat must I not break, and where is it dangerous?invariants · public contracts · test coverage gaps · blast radius · policy & compliance zones DERIVED
L7 MemoryWhat have we learned since the last build?agent sessions · task outcomes · human corrections · refuted claims · decay ACCUMULATED

L4 is the layer that makes legacy tractable. Structure tells you a function exists; only history tells you it was rewritten three times, each rewrite followed by an incident, and that two teams both depend on its exact timing. That is the knowledge that leaves with people.

The honesty model

Every fact in every layer carries the same envelope, and packs can be filtered on it. This is what makes a Brain safe to hand an autonomous agent.

FieldCarriesUsed for
evidencefile:line spans, commit SHAs, CI log refsAgent can re-read the source of any claim
methodEXTRACTED · DERIVED · INFERRED · OBSERVED · ASSERTEDTrust tiering; "extracted only" mode
confidence0.0 – 1.0, adjusted by verificationRanking inside a context pack

05

The context pack compiler

The centerpiece. Given a task, a token budget, and an agent role, it compiles the smallest bundle of cited facts sufficient to do the job correctly.

This is graph traversal with typed expansion and a budget fit — not similarity search over chunks. Embeddings help resolve a fuzzy task description to concrete anchors; everything after that is structural, which is why the result is explainable and reproducible.

Three surfaces

The same Brain is reached three ways. An MCP server for agents, exposing locate, explain, impact, contract, precedent, runbook, pack, and the write-back tools assert and question. A CLI for humans and CI. And the generated Atlas — Markdown and HTML — for review, onboarding, and the moment a human needs to audit what the machine believes.

06

A Brain is alive

A snapshot rots within a week. The operating model is a loop that runs on every commit and every agent session.

Serving the lifecycle

Each stage of the software lifecycle reads specific layers and writes specific facts back. That two-way traffic is the whole design.

StageReadsWrites back
UnderstandAtlas, L1 structure, L3 semantics, L4 intentOpen questions, gaps found
PlanPack: blast radius, contracts, precedentProposed change set, risk estimate
ImplementPack: constraints, conventions, ownersNew symbols, edges, decisions taken
TestL5 runbook, L6 coverage gapsObserved commands, verified claims
ReviewImpact diff, invariant checks, Brain diffHuman corrections, asserted facts
ShipL5 pipelines, environments, rollout pathsDeploy topology, real dependencies
OperateL2 behavior, L6 danger zones, ownershipIncidents, hotspots, runtime truth
LearnL7 memory, outcome historyRefuted claims, refined confidence

From repo to system: the Cortex

One Brain models one repository. Real organizations are systems of systems, so Brains federate into a Cortex: a higher-order index over many Brains that resolves cross-repo contracts, builds the true service graph from both code and traffic, carries org-wide policy, and answers questions no single repository can — which twelve services break if this field changes type? A Cortex is composed, never re-extracted; each Brain stays authoritative for its own repo.

07

Living inside an agent harness

Claude Code is the reference integration, and the sharpest test of the design: if a Brain cannot make a real coding agent measurably better inside a real harness, nothing else here matters.

CodeBrain ships as a CLI plus an MCP server and attaches through four seams. The important one is not the tool surface — it is the hooks, because they place the right context into the session without the model having to decide to ask for it. A tool that must be chosen will sometimes not be chosen.

What lands in the repository

.brain/                    # the Brain — committed, diffed, reviewed
  manifest.json          # schema version, as_of commit, build config
  layers/                # l0_corpus … l7_memory, JSONL, sorted, line-diffable
  claims.db              # derived index, gitignored, rebuilt from layers/
  ATLAS.md               # human-readable, generated
.mcp.json                  # exposes the Brain as an MCP server
.claude/settings.json       # the five hooks
CLAUDE.md                  # generated stanza: invariants + consult-the-Brain-first

The five hooks

HookCommandWhat it does
SessionStartcodebrain briefInjects a ~400-token orientation: what this repo is, its modules, current branch, which regions are stale
UserPromptSubmitcodebrain packReads the task off stdin, compiles a scoped pack, prints it into context — the agent is informed before its first action
PreToolUsecodebrain guardChecks the pending edit against L6 constraints; can deny with a reason, or warn on hotspots and frozen zones
PostToolUsecodebrain touchMarks the edited neighborhood stale so the next pack does not serve outdated facts
Stopcodebrain learnHarvests the session into L7 and triggers an incremental sync

Alongside them, an MCP server exposes brain_locate, brain_explain, brain_impact, brain_contract, brain_precedent, brain_runbook, brain_pack, and the write-back pair brain_assert and brain_question — for the mid-task moment when the agent realises it needs more. A generated CLAUDE.md stanza carries policy and the repo's hard invariants, kept deliberately short because the hooks carry the volume. A /brain skill is the human entry point.

One session, concretely

Task: add rate limiting to the payments API. Without a Brain, the agent greps for "rate limit", finds nothing, greps for "middleware", opens eight files, spends roughly 25k tokens rebuilding the request path — and never discovers that a house-standard RateLimiter already exists in a shared package. With a Brain, the prompt hook fires first:

CONTEXT PACK · task: add rate limiting to the payments API · 5.8k/6k tokens

ANCHORS       payments/api.py:44 charge_endpoint · payments/middleware.py:12 chain
BLAST RADIUS  4 internal callers; POST /v1/charges has 4 external consumers   [EXTRACTED]
CONTRACTS     openapi.yaml#/paths/~1v1~1charges — response shape frozen       [EXTRACTED]
PRECEDENT     throttle added to /v1/refunds in a1c93f2 (Mar 2026) using
              packages/shared/throttle.py:RateLimiter — the house pattern    [DERIVED 0.86]
CONSTRAINTS   payments/settle.py is PCI-scoped, CODEOWNERS @risk-eng — frozen [ASSERTED]
              payments/api.py: 31 commits/90d, 3 followed by incidents       [DERIVED]
RUNBOOK       make test-payments                          [OBSERVED, verified 9f21ab, 41s]
UNKNOWNS      Redis vs in-process limiter store — not statically determinable

The agent then uses the house pattern instead of inventing one; is denied by guard when it wanders into PCI-scoped settle.py, and routes around rather than silently editing frozen code; verifies with the real test command rather than guessing between pytest and make. On stop, learn records the new symbols, confirms the runbook claim and raises its confidence, and resolves the Redis unknown — so the next agent never rediscovers it.

Two rules this integration must not break

Every hook fails open. If .brain/ is missing, stale, or the binary errors, hooks print nothing and the harness behaves exactly as it does today. A Brain that can break someone's session gets uninstalled the first time it does — so degradation is a hard requirement, not a nicety.

The cold build is the only slow moment. First extraction on a large legacy monorepo is where adoption is won or lost; everything after is incremental. That is why P1's sixty-second target is a gate and not a vanity number.

08

Roadmap

Sequenced so that each phase ships something usable on its own, and so the deterministic, verifiable core exists before any dependency on language-model output. Durations assume a small focused team.

P02 weeks

Schema and skeleton

The Brain data model, the provenance envelope, on-disk format and store, CLI shell, and the plugin contract for extractors. Nothing clever — but everything downstream conforms to it, so getting the envelope right is the whole job.

Done whenA Brain can be written, read, merged and diffed, and two dummy extractors coexist behind the provider interface.
P14 weeks

Deterministic core — L0, L1, L4, L5

Corpus detection; structural extraction for Python, TypeScript and JavaScript; operations discovery from CI configs, manifests and scripts; git archaeology producing churn, hotspots, co-change coupling and ownership. The Atlas generator. All offline, no API key, fully reproducible.

Done whencodebrain build on a 100k-LOC repo finishes under 60 seconds offline and produces an Atlas a new engineer can genuinely onboard from.
P24 weeks

Context packs and MCP — first agent value

Anchor resolution, typed expansion, blast-radius computation, budget knapsack, and the MCP server exposing the tool surface. The evaluation harness starts here and runs permanently from now on.

Done whenOn a held-out task set, an agent given only a pack beats the same agent with plain search on task success rate and tokens-to-solution — measured, not asserted.
P34 weeks

Verification and drift — the moat

Executable claims, sandboxed runbook verification, promotion and demotion of confidence, incremental sync, staleness tracking, and the CI drift gate. This is where CodeBrain stops being a document generator.

Done whencodebrain verify promotes verified claims and demotes refuted ones automatically, and CI fails a pull request whose Brain has drifted from HEAD.
P44 weeks

Semantics, behavior and constraints — L2, L3, L6

Runtime surface mapping — entrypoints, routes, jobs, data access, config. Language-model passes for the domain model, bounded contexts and ubiquitous language, every claim cited. ADR and pull-request mining for narrative intent. Constraints derived from invariants, coverage gaps and hotspot overlap.

Done whenThe Brain answers "why does this exist and what breaks if I change it" with citations a reviewer can check in under a minute.
P54 weeks

Memory and write-back — L7

Session ingestion, human corrections, refuted-claim tracking, confidence decay, and conflict resolution when agents disagree with the Brain or each other.

Done whenA second agent measurably outperforms the first on a related task purely because of what the first wrote back.
P66 weeks

Cortex — systems of systems

Federation across Brains, cross-repo contract resolution, the composed service graph, org-wide policy and constraint inheritance, and cross-repo impact analysis.

Done whenA field type change in one repository correctly enumerates its consumers in every other repository in the Cortex.
P7ongoing

Platform

Hosted Brains, team dashboards, policy administration, more languages, and a third-party extractor ecosystem. Only worth starting once P2 and P3 have proven the value is real.

Done whenTeams outside the founding one keep their Brains green without being asked to.

How we will know it works

"The graph has 40,000 nodes" is not evidence of anything. From P2 onward, every change is judged against a held-out task set on these numbers.

10

What could kill this

Over-trust in a wrong Brain

The worst failure mode by far. A confidently wrong fact scales its damage across every agent that reads it — far more harmful than a gap.

MitigationProvenance on every claim, verification by execution, refutation tracking, and packs that surface unknowns rather than hiding them.

Staleness

A Brain that lags HEAD becomes actively misleading within days on an active repository.

MitigationIncremental sync on every commit, drift as a CI gate, and staleness carried in the envelope so consumers can discount it.

Extraction fidelity across languages

Dynamic dispatch, reflection, code generation, DI containers and macros defeat static analysis — precisely the patterns legacy enterprise code is built from.

MitigationRuntime observation as a first-class source (OBSERVED facts), explicit low-confidence marking, and honest coverage reporting per language.

Cost at scale

If every build needs a large language-model pass over the whole repository, the economics fail on exactly the monorepos that need this most.

MitigationDeterministic-first by design; inference confined to L3 and narrative L4, incremental, cached, and re-run only for changed neighborhoods.

Scope creep into an IDE, a platform, or a graph database

The concept is broad enough to justify building almost anything, which is how this ends up as a demo with nine half-layers.

MitigationP1 must stand alone as a useful offline tool; nothing in P4 or later starts until P2 and P3 have measured a real lift.
